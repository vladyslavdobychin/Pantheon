How one turn flows

The Runner drives a loop. It asks the current player's Agent for a Move, hands that to the pure Core, which mutates GameState and returns a list of fat events the View just plays. The two gold payloads are already your network protocol.

  1. 1Runner awaits the current player's agent — await agent.DecideAsync(view). The loop suspends; Unity stays responsive.
  2. 2Agent returns a Move — the player's intent. This is your network request.
  3. 3Runner calls the pure Core — Core.ApplyMove(state, move), crossing into the headless boundary.
  4. 4Core mutates GameState in place and appends fat events to the log.
  5. 5Core returns a List<GameEvent> — the result. This is your network response.
  6. 6Runner plays the events to the View, which just animates and shows numbers — no rules.
  7. 7The player clicks; input becomes the next agent's Move, and the loop turns again.

The five decisions this rests on

Each closed a real fork. Together they make the diagram above the only shape that's consistent.

State model Mutable + Clone()

Entities update in place. To try a move the AI clones the whole state, applies, scores, discards. Simpler than immutability, and the shape SabberStone ships.

Randomness One seeded PRNG

Lives inside GameState; every roll goes through it. The game becomes pure(seed, moves) — replay, deterministic tests, no client-side re-rolls.

Events Fat semantic events

A semantic name (MinionAttacked) carrying its deltas (3→1). The view needs zero rules; netcode still gets the exact numbers.

Core shape Sync step function

StartGame / GetValidMoves / ApplyMove. Pure, Unity-free, trivially testable. State is passed in — like a stateless service.

Input seam Async Runner + IAgent

The loop awaits a Task<Move>. Local, AI, and network players are just implementations — swap the agent, not the loop. This is why PvE and PvP are one engine.
